# Добавление источника обогащения

Источник — тонкий клиент к внешней системе: по `entity_id` отдаёт `dict`.
Реестр (`app/enrichment/registry.py`) наполняется на импорте модулей,
роутер `GET /api/v1/enrich/{source}/{entity_id}` достаёт источник по имени.
Добавление источника = один новый модуль + одна строка импорта. Ничего
другого трогать не нужно.

## Что выяснить до кода

Если не сказано в запросе — спросить, не додумывать:

1. **Имя в реестре** — оно же сегмент URL (`courses`, `employees`).
2. **Откуда данные**: мок/статика на первое время или реальная внешняя
   система (тогда — какой протокол, какие настройки, какой клиент;
   новый HTTP-клиент — это новая зависимость, её нужно согласовать).
3. **Форма `data`** — какие поля отдаём наружу.
4. **Пример `entity_id`** и что считается «сущности нет».

## Шаги

### 1. Скопировать шаблон

```
.claude/skills/add-datasource/assets/source_template.py
  → app/enrichment/<name>.py
```

Копировать, а не писать с нуля. Причина не в экономии печати:

- **Инварианты слоя не восстанавливаются по памяти.** Их четыре, и каждый
  ломается молча: регистрация именно на импорте модуля; `dict(...)` —
  возврат копии, иначе вызывающий мутирует наши данные; `EntityNotFound`
  против общей `EnrichmentError` (роутер разводит их в 404 и 502 — перепутать
  значит отдавать 502 на опечатку в id); совпадение с `Protocol` по форме,
  без наследования.
- **Написанный с нуля модуль выглядит правильным и проходит happy-path.**
  Расхождения всплывают на границах: чужой мутации, чужом 404, дубле имени.
- **Шаблон делает шаг механическим** — «заполнить TODO», а не «вспомнить
  архитектуру». Проверяемо: непроставленных TODO не осталось.

Дальше: переименовать класс (`TemplateSource` → `<Name>Source`), проставить
`name`, заполнить TODO, удалить неиспользуемый вариант `fetch()`.
Ориентир живого источника — `app/enrichment/courses.py`.

### 2. Включить в реестр

В `app/enrichment/__init__.py` — импорт рядом с существующим:

```python
from app.enrichment import <name>  # noqa: F401 — регистрирует <Name>Source
```

Без этой строки модуль никто не импортирует, `register()` не выполнится,
и источник не появится ни в реестре, ни в 404-подсказке роутера.

### 3. Настройки (только если внешняя система)

Хост, ключи, таймауты — в `app/config.py` (pydantic-settings) и env.
Хардкоженных URL и секретов в модуле источника быть не должно.

### 4. Тесты

Дописать в `tests/test_enrich.py`, повторяя тамошний стиль:

- `fetch()` на существующем id → ожидаемый `dict`;
- `fetch()` на неизвестном id → `pytest.raises(EntityNotFound)`;
- источник в `source_names()` после импорта пакета;
- `GET /api/v1/enrich/<name>/<id>` через фикстуры `client` + `auth_headers`
  → 200 и точный JSON.

Регистрируешь что-то вручную в фикстуре — снимай через `unregister()`
в teardown, иначе следующий тест упадёт на дубле имени.

### 5. README

Перечислить источник: имя, что отдаёт, пример `entity_id`. Раздела про
источники обогащения может ещё не быть — тогда завести и заодно внести
`/api/v1/enrich/{source}/{entity_id}` в таблицу эндпоинтов.

### 6. Проверка

Выполнить skill `/verify` (минимум — `uv run pytest -q`), показать результат.
Затем пройти по `references/checklist.md` и отчитаться по пунктам. Шаг
не «готово», пока чек-лист не закрыт целиком.

## Границы

- Контракт `EnrichResponse` не менять — только форма `data` у нового источника.
- `base.py`, `registry.py`, `routers/enrich.py` при добавлении источника
  не правятся. Понадобилось — значит задача другая: остановиться и сказать.
- Ошибки внешней системы поднимать как `EnrichmentError`, не глушить:
  502 здесь — правильный ответ (правило «ошибки агента → 200» относится
  к `/chat`, к обогащению оно не применяется).
